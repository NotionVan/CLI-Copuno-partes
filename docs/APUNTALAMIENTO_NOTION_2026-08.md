## Descartado y por qué

- **Lock database como control de I9/P1** — no es seguridad: reversible por cualquier editor y sin cobertura documentada del título ni de Manage data sources. Se usa solo como segundo cinturón (dossier GOBERNANZA).

- **Migrar tramos del pipeline a Workers o File Upload API ahora** — ADR-008 vigente (criterios de reapertura sin cumplir) y congelación pre-demo; solo se verifica la fecha de facturación.
- **Synced databases como espejo de solo lectura para oficina** — solo existen para Jira/GitHub/Asana; la vía es Can view + linked views (cuyos filtros NO son frontera de seguridad).
- **Sub-items para Parte→Detalle Horas** — meterían la jerarquía en una sola BD con soporte API incompleto (issue #696); la relación entre dos BDs actual es superior.

## Apéndice — resúmenes de los 5 bloques del dossier


### Guías técnicas (developers.notion.com)

El portal developers.notion.com se reorganizó en 2026 (guides/get-started + guides/data-apis + workers/ + guides/mcp/) y contiene varias piezas que atacan directamente nuestros riesgos vivos. (1) WEBHOOKS: existen suscripciones de webhook para conexiones internas con eventos de esquema — data_source.schema_updated, data_source.created, page.properties_updated — que detectarían en minutos exactamente los dos incidentes que nos preocupan: el renombre del título de la BD Empleados (I9) y la creación de una 2ª data source (P1). Firma HMAC-SHA256, 8 reintentos en 24 h, entrega at-most-once y sin payload completo (hay que re-leer por API); patrón oficial: webhook para invalidar cache + polling como red de seguridad — encaja con nuestra queja recurrente "la app no actualiza". (2) RIESGO P1 CONFIRMADO OFICIALMENTE: la guía de upgrade 2025-09-03 dice textualmente que en versiones antiguas (nosotros: 2022-06-28), si el usuario añade otra data source a una BD, fallan creación de páginas, lecturas, escrituras, queries y relaciones hacia esa BD. La mitigación de fondo es migrar a 2025-09-03+ (hoy la vigente es 2026-03-11, con cambios menores: archived→in_trash, position en bloques); la mitigación barata es el webhook data_source.created como alarma. (3) RESILIENCIA A RENOMBRES: la guía de databases recomienda leer el esquema dinámicamente y permite referenciar propiedades por ID en vez de por nombre — inmune a renombres tipo I9 y a nuestras propiedades con espacio final. (4) Guía nueva de queries grandes: tope duro de 10.000 resultados por query con request_status="incomplete" (no lo comprobamos hoy), estrategia de ventanas por created_time — relevante cuando Partes crezca con 20 usuarios. (5) URLs de ficheros (Documento Firmado) son enlaces S3 firmados que caducan en 1 h — nunca persistirlas; re-leer la página antes de servir. (6) Notion Workers (beta, de pago desde 11-ago-2026 vía créditos): runtime Node/TS alojado por Notion con webhook triggers, syncs programados (solo unidireccionales HACIA Notion — no sirve para ADR-007 Supabase-como-caché) y agent tools — insumo directo para el ADR-008 Workers-vs-Make. (7) MCP oficial (mcp.notion.com): 20 tools, OAuth, 180 req/min; útil como herramienta de diagnóstico OAuth contra el workspace del cliente, no sustituye a la integración del servidor. (8) External Agents API en alpha privada con waitlist — aún no accionable. (9) Buenas prácticas de tokens (refuerzan cerrar E1 de Make): un token por entorno/servicio, rotación, secret scanning, inventario; los PAT nuevos caducan al año (los de conexión interna no). (10) Los ejemplos oficiales del SDK migraron a github.com/makenotion/notion-cookbook e incluyen justo nuestra arquitectura (Express + form) y patrones de sync unidireccional con acciones externas.


### Seguridad y gobernanza del workspace

Conclusión central: el "Lock database" de Notion NO es un control de seguridad (cualquiera con edición lo desactiva y solo protege propiedades y vistas); el control real contra I9/P1 es el nivel de permiso "Can edit content" en cada BD, que impide cambiar estructura (propiedades, vistas, sorts, filters), impide bloquear/desbloquear y — al requerir "Can edit" el añadir data sources y "Full access" el moverlas — también cierra la puerta a la 2ª data source. Confirmado además en docs de developers que una BD con múltiples data sources ROMPE la API antigua (2022-06-28: validation_error en read/write/query y create page), así que P1 tumbaría la app entera. El audit log (que registra literalmente "Data source schema edited" y "Data source created") es solo Enterprise, igual que disable export/publishing y la retención de papelera personalizable; en Plus/Business la vigilancia de esquema hay que montarla por API (canario diario de esquema con el NOTION_TOKEN ya disponible). Procedimiento de endurecimiento concreto incluido como hallazgo. Red de seguridad existente sin coste: propiedades borradas recuperables desde "Deleted properties" de la BD, papelera 30 días, page history 30 días (Plus) / 90 (Business), export manual de workspace por el owner (sin export programado nativo).


### Automations nativas, botones y charts

Las automations nativas de Notion (triggers: page added / property edited / recurrente; acciones: editar propiedades, crear-editar páginas en otra BD, notificación in-app hasta 20 personas, Slack, email vía Gmail, webhook POST y variables) NO pueden sustituir los tramos pesados del pipeline Make — generar el PDF (3/4), subir el Documento Firmado (4/4) y la limpieza en OneDrive quedan fuera por diseño: la acción webhook es solo POST, solo envía propiedades (nunca contenido ni ficheros) y no hay acción que escriba en propiedades files ni toque APIs externas más allá de ese POST. Donde SÍ aportan sin token y sin Make: (1) notificaciones internas al cambiar Estado (p. ej. avisar a oficina cuando un parte pasa a Firmado) — Copuno está en Business, así que están disponibles; (2) un botón/automation "property edited → send webhook" PUEDE apuntar directamente a los webhooks de Make (la ayuda oficial cita Make como receptor compatible), pero no elimina pasos hoy: el payload de la automation no cumple el contrato E3 de las data structures 608077/608078 (habría que hacer un webhook pasarela o relajar la validación), el payload no es previsualizable ni está documentado (hay que capturarlo con webhook.site), NO hay reintentos y al primer fallo la automation SE PAUSA en silencio (solo un icono de exclamación) — fiabilidad inferior al POST del server con lock optimista; además está sin confirmar si las ediciones hechas por la integración API disparan el trigger (prueba de 10 min pendiente). El hallazgo más valioso para "apuntalar" es otro: los webhooks de integración de la API (gratuitos, con firma HMAC y 8 reintentos en 24 h) incluyen los eventos data_source.created y data_source.schema_updated (API 2025-09-03) — exactamente el sistema de alarma que habría detectado I9 (renombre de título) y que cubre el riesgo P1 (segunda data source): suscribir el backend de Vercel a esos eventos es la mejora de infraestructura más barata y directa. Complementos: charts nativos ilimitados en Business para un dashboard de partes por obra/estado (sin desarrollo); fórmulas 2.0 para validaciones previas al envío; y ojo con Workers: la propia doc de Notion se contradice sobre cuándo empiezan a consumir créditos (11-ago-2026 en la página de precios vs 15-oct-2026 en el help center) — el criterio de reapertura nº1 del ADR-008 asume el 15-oct, conviene mirar el panel de créditos del cliente porque la fecha de agosto ya habría pasado. Notion Calendar ya soporta Outlook (jun-2026, Microsoft Graph) pero ni Mail ni Calendar tocan la operativa de partes.

### Modelo de datos y rendimiento de producto

Documentación de producto de Notion peinada (help center oficial + release notes + 2 fuentes terceras fiables para límites no publicados). Lo esencial para Copuno: (1) los límites duros oficiales (250.000 filas/BD, 500 propiedades, 2,5 MB por página, 10.000 referencias por página en relaciones bidireccionales) quedan lejísimos del volumen actual (Empleados 1.554, Partes ~190), pero Detalle Horas es la BD que crecerá más rápido con 20 usuarios y la degradación práctica de UI empieza en 5-10k filas según la comunidad — la API con filtros no sufre igual, así que el riesgo es para las vistas del workspace del cliente, no para la app. (2) El riesgo P1 (2º data source) está confirmado en la FAQ oficial de developers: con la versión API 2022-06-28 que usa server.js, una BD con múltiples data sources devuelve error de validación "multiple_data_sources_for_database" — la app se rompería para esa BD; cualquier usuario con Can edit puede añadir un source en 2 clics y no existe bloqueo específico (Lock database solo protege propiedades/vistas y es reversible por cualquiera con edición). La mitigación real es permisos (Can view para oficina, edición restringida sobre las 6 BDs fuente) o migrar la API a 2025-09-03. (3) Para "vistas seguras de solo lectura de oficina": synced databases NO sirven (son solo integraciones Jira/GitHub/Asana); la vía es linked views + permiso "Can view" en la BD fuente — los filtros de un linked view NO son frontera de seguridad, heredan permisos del source y no se puede fijar acceso distinto por source. (4) Recurring templates existen (diaria/semanal/mensual, con hora) y una relación pre-rellenada apunta siempre a las mismas páginas — serviría para plantillas semanales por obra, pero los partes nacidos así esquivarían server.js (sin Detalle Horas, sin invalidación de cache): útiles como BD de planificación semanal de personal, no para crear partes. (5) Sub-items/dependencies no aportan al esquema (viven dentro de una misma BD; Parte→Detalle Horas ya es relación entre dos BDs y con soporte API completo, que sub-items no tiene). (6) Fórmulas: cadena máxima de 15 propiedades referenciadas (falla en silencio al excederla) y error de profundidad a 10 tablas — las fórmulas actuales (Firmar, Es Rectificativo) están lejos. (7) Guía oficial de rendimiento: filtrar vistas por propiedades simples (status/select/fecha, no fórmulas ni rollups), minimizar cadenas fórmula→rollup, linked views en vez de inline en páginas concurridas, archivar antiguos por Created time. (8) Notion AI/Agents completo solo en Business/Enterprise (~19,50 €/miembro/mes); los Agents editan cientos de páginas de golpe respetando permisos — si el cliente lo activa, es un nuevo vector de ediciones masivas tipo I9 y conviene pactarlo.
